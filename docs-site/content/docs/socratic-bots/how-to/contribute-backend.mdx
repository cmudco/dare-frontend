Thanks for helping with the Socratic Bots backend, the teaching-layer API that runs alongside DARE.
To get a working stack first, follow
[docs/tutorials/quickstart.md](/docs/socratic-bots/tutorials/full-stack-quickstart).

## Filing issues

1. **Search first.** Look through
   [open and closed issues](https://github.com/cmudco/socraticbots-backend/issues?q=is%3Aissue), and
   check that the problem still happens on the latest `dev`.
2. **Pick the right repo.** Many problems are DARE configuration, so check the quick start's
   [Troubleshooting](/docs/socratic-bots/tutorials/full-stack-quickstart#troubleshooting) first. The bug form asks which
   service fails; pick "Not sure" if you don't know.
3. **Open a form.** Go to
   [Issues → New issue](https://github.com/cmudco/socraticbots-backend/issues/new/choose) and choose
   **Bug report**, **Feature request** or **Docs problem**. Each form asks for exactly what we need;
   fill in every required field.
4. **Redact.** Remove keys, tokens and student data from logs and screenshots.
5. **Watch the issue.** If we need more detail, we ask there.

Before a large change, such as a new app, a new DARE endpoint, or a change to the voice runtime
contract, open a feature request with a short design sketch and wait for a reply before you write
code.

Security vulnerabilities never go in an issue. Follow [SECURITY.md](/docs/socratic-bots/reference/backend-security).

## Pull requests

### Branching

`dev` is the integration branch; open pull requests against `dev`, not `main`.

```bash
git checkout dev
git pull --ff-only origin dev
git checkout -b <your-name>/<feature|fix|refactor|docs>/<short-description>
```

### Before you open a PR

Run these from `backend/` with your virtualenv active, or run the `check` skill:

```bash
python manage.py check
python manage.py makemigrations --check --dry-run   # no missing migrations
python manage.py test                               # SQLite, no DARE or network needed
```

The tests need `SSO_JWT_KEY` and `DARE_INTERNAL_KEY` set (any value works; the `.env` from the quick
start is enough). Follow [docs/reference/rules.md](/docs/socratic-bots/reference/backend-rules); its Definition of
done lists what reviews check.

### PR description

The `pull request template` asks for what, why, how, testing and AI
assistance, plus a checklist. Fill in every section; write "none" where nothing applies. For a
change that spans repos, link the other PRs and give the deploy order.

### Review and merge

- One approving review from a maintainer.
- Maintainers squash-merge by default, so the PR title becomes the commit subject.

### Commit messages

`<type>: <summary>`, where type is `feat`, `fix`, `refactor`, `docs`, `test`, or `chore`. Keep the
summary under 70 characters and use the body for the reasoning.

```
fix: keep tutor budgets in sync after a model is deleted

DARE now calls nullify-model before deleting a model, so tutors fall
back to the group default instead of failing the next chat.
```

## Using AI coding agents

- `AGENTS.md` holds the commands and traps; Codex reads it directly and `.claude/CLAUDE.md` imports
  it for Claude Code.
- Skills (`run-backend`, `check`) live in `.agents/skills/<name>/SKILL.md`; `.claude/skills/` holds
  symlinks to them. Invoke one by name (`/run-backend` in Claude Code, `$run-backend` in Codex). See
  `.agents/README.md`.
- Treat these files like code: if you change how the backend is run or tested, update the matching
  skill in the same PR.
