Thanks for helping with the Socratic Bots frontend, the browser app that sits on the Socratic Bots
backend and DARE.

## Filing issues

1. **Search first.** Look through
   [open and closed issues](https://github.com/cmudco/socraticbots-frontend/issues?q=is%3Aissue),
   and check that the problem still happens on the latest `dev`.
2. **Pick the right repo.** A failed login or a missing chat reply usually comes from backend
   configuration; the
   [quick start troubleshooting list](/docs/socratic-bots/tutorials/frontend-quickstart#troubleshooting) covers the
   common ones. The bug form asks which service fails; pick "Not sure" if you don't know.
3. **Open a form.** Go to
   [Issues → New issue](https://github.com/cmudco/socraticbots-frontend/issues/new/choose) and
   choose **Bug report**, **Feature request** or **Docs problem**. Each form asks for exactly what
   we need; fill in every required field.
4. **Redact.** Remove keys, tokens and student data from logs and screenshots.
5. **Watch the issue.** If we need more detail, we ask there.

Before a large change, such as a new page, a change to a socket payload, or a new dependency, open a
feature request with a short design sketch and wait for a reply before you write code.

Security vulnerabilities never go in an issue. Follow [SECURITY.md](/docs/socratic-bots/reference/frontend-security).

## Pull requests

### Branching

Fork the repository and branch from the latest `dev`. Pull requests target `dev`.

```bash
git checkout dev
git pull --ff-only origin dev
git checkout -b your-name/feature/short-description
```

Branch names follow `<author>/<feature|fix|refactor|docs>/<short-description>`.

### Before you open a PR

Run the checks (or the `check` skill). All of them pass on `dev`; keep it that way.

```bash
npm run lint
npm run format:check
npm test
npm run test:voice-contract
npm run build
```

- Follow [docs/reference/rules.md](/docs/socratic-bots/reference/frontend-rules); its definition of done is the bar.
- Test the change in a browser against a local Socratic Bots backend and DARE. If you touched chat
  sockets, also run the browser-console regressions in `tests/README.md`.
- If you change a socket payload or event, update
  `tests/SOCKET_CONTRACT.md` and coordinate the matching DARE change.
- The Husky pre-commit hook runs Prettier and ESLint on staged files. Run Prettier only on files you
  changed (`npx prettier --write <files>`), never `npm run format`.

### PR description

The `pull request template` asks for what, why, how, testing, screenshots
and AI assistance, plus a checklist. Fill in every section; write "none" where nothing applies. If
the change needs a backend or DARE change, link that PR and say which to deploy first.

### Review and merge

- At least one approving review from a maintainer.
- Squash-merge by default, so make the PR title a good commit message.

### Commit messages

`<type>: <summary>`, where type is `feat`, `fix`, `refactor`, `docs`, `test` or `chore`. Keep the
summary under 70 characters and use the body for context.

```
fix: keep the composer locked until the final chat message arrives
docs: list every environment variable in configuration.md
```

## Using AI coding agents

`AGENTS.md` holds the project instructions; `.claude/CLAUDE.md` imports it for Claude Code.
Procedures (`run-frontend`, `check`) live in `.agents/skills/`, with symlinks in `.claude/skills/`;
see `.agents/README.md`. Invoke one by name (`/run-frontend` in Claude Code,
`$run-frontend` in Codex). If you change how the app is run, built or tested, update the matching
skill in the same PR.

## Getting help

Open an issue (with a design sketch before a large change) or a draft PR and ask in the description.
